## VB-34 · The splash
On load, before anything else: the animated mark, **camera slowly changing perspective in a
loop** — cinematic rather than a spin — with the Workbrain lockup centred and the tagline beneath.

> **AI does the work. You do the thinking.**

The maths already exists. `src/core/geometry/icosahedron.ts` is pure and `markSpin.ts` already
drives a rotating camera; this is a different camera path (drifting orbit, easing between
perspectives) over the same solid. Do not re-derive the geometry.

**Constraints**: `prefers-reduced-motion` gets a still, composed frame — the tagline and lockup
must carry the moment without motion. And a splash that delays someone reaching their work is a
tax paid on every open: it should be skippable by any input, and it must not gate the panel's first
paint. Decide deliberately whether it shows once per session or on every open; on every open will
wear out fast.

**Accept**: loops smoothly without a visible seam; reduced motion is a still frame with the same
information; any click/key skips it; never blocks input; the tagline is in `strings.ts`.

## VB-35 · ⚠️ Connect a folder
**This is an architectural change, not a feature.** Today the product's identity is *"everything
lives in your browser."* Mapping a folder on disk makes it a file-backed app. That is arguably
better — it is more local-first, not less — but it is a different product to describe.

The flow Adam wants: if no folder is mapped, the first thing offered is **connect a folder**, which
establishes (a) where new files get created and (b) what is being monitored. Once mapped — now or
in a previous session — load straight to Home.

**What this collides with, concretely:**
- `store/PRIVACY.md`, which I wrote three commits ago, says *"Everything you type into Workbrain is
  saved in your own browser using Chrome's extension storage."* That becomes untrue.
- The store listing's *"It works offline. It works on a plane."* stays true. Good.
- `docs/ARCHITECTURE.md`'s storage model assumes `chrome.storage` is the only persistence.
- R1-10's download/import flow may become redundant, or may become the fallback for people who
  decline the folder. Decide which.

**Open, and blocking**: what happens when someone declines, or the handle goes stale (folder moved,
permission revoked)? `docs/GUARDRAILS.md`'s degradation table is absolute — every enhancement falls
back to the manual path silently. So the folder must be an *upgrade* over `chrome.storage`, never a
requirement. If the product can't work without it, it breaks a guardrail.

### What the capability survey found (2026-08-24, Chrome 151, empirically probed)

**It works, and it costs no manifest permission.** `showDirectoryPicker()` is a web API on our own
extension page — verified functional, and **invisible to the store's permission list**. No new
install warning, no new permission string.

**Handles persist.** A `FileSystemDirectoryHandle` structured-clones into IndexedDB and reads back
with `isSameEntry: true` — verified round-trip.

**Writing needs no per-write gesture.** Once `readwrite` is granted:
`getFileHandle(name, {create:true})` → `createWritable()` → `write()` → `close()`. Autosave is fine.

**Folder watching is real, not polling.** `FileSystemObserver` has been enabled by default since
Chrome 133 desktop and was constructed and `observe()`d successfully. Supports `{recursive: true}`.
Caveats: non-standard, Chromium-only, an undisclosed per-origin cap, and a `"unknown"` change type
that means re-enumerate. **Keep polling as the documented fallback** — the degradation rule applies.

**TWO THINGS MUST BE TESTED BY HAND BEFORE BUILDING. Both are ten-minute checks.**
1. **Does `showDirectoryPicker()` work in the actual side panel?** There is a known Chromium bug
   where the picker aborts — but it is *popup*-specific (the popup closes when the picker takes
   focus). A side panel does not close on focus loss, so it should be fine. Unverified: Playwright
   cannot open the real panel.
2. **Does a `chrome-extension://` origin get "Allow on every visit"?** Chrome 122+ offers persistent
   permission, but the documentation describes it for web origins and installed web apps and is
   **silent on extensions**. If extensions do not get it, the person re-approves the folder on
   every browser restart — which is a materially different product, and would change whether this
   is worth building at all.

**Store position**: the zero-collection claim survives, but the 2026-08-01 policy update says
collected data must be *strictly necessary to the disclosed single purpose* and all collection
disclosed *regardless of relevance* — and neither policy defines "collect" as excluding on-device
data. So the permission justification must state plainly that the folder is user-chosen, never
leaves the device, and is never transmitted. Also watch **single-purpose creep**: folder mapping +
monitoring + composer injection can read as three products. Frame all of it as "maintains your
context file."

## VB-40 · ⚠️ Point at the AI's prompt box
Copy a prompt, then have the panel show where to paste it in the detected AI site.

**This is explicitly out of scope for Release 1** (`docs/RELEASE-1.md`: *"Fill-only hand-off · any
host permission"*), and it is Permission **Tier 1** in `docs/GUARDRAILS.md` — requested only when
the person clicks "put it in <AI> for me", never at install. The manifest already declares the four
origins under `optional_host_permissions`, so the architecture anticipated it.

**What it costs**: the store listing I wrote says *"No host permissions are requested at install…
declining them leaves the extension fully functional."* That stays true only if the permission is
genuinely optional and genuinely in-context. Detecting the site at all needs either an optional host
permission or `tabs` — and `tabs` is banned outright by GUARDRAILS.

**The cue engine (R1-08) was built for exactly this** — `point:target|label` parses today and
no-ops, with a comment saying cross-tab pointing needs a host permission this release doesn't have.
That is the seam.

### What the capability survey found — this one is harder than it looks

**Opening the side panel does not grant `activeTab`.** That is deliberate Chromium behaviour
([crbug 336592430](https://issues.chromium.org/issues/336592430)), not a bug: the panel is
persistent, so there is no clear moment of invocation. **With only `storage` + `sidePanel` we
cannot learn the tab's URL at all** — `tabs.query()` runs but strips `url`/`title`/`favIconUrl`,
and the `url` filter is ignored.

`activeTab` is invoked by exactly four things: an action click, a context-menu item, a `commands`
shortcut, or an omnibox suggestion. **There is a trap**: we set
`setPanelBehavior({openPanelOnActionClick: true})`, which means `action.onClicked` never fires — so
the action-click route is already closed to us. `commands` or `contextMenus` are the free triggers.

**The zero-warning shape**, if this gets built: `declarativeContent` to light the icon on the four
origins (URL matching with no host access, no warning), plus a `commands` shortcut or context-menu
item to actually read the URL via `activeTab`. Then the existing Tier-1 design
(`optional_host_permissions` + `scripting`, prompted on click) for writing into the composer. That
is already the right architecture.

**`tabs` is banned and should stay banned** — it costs the *"Read your browsing history"* warning,
which is exactly the install-time fright `docs/GUARDRAILS.md` exists to prevent.

**One free win found**: `navigator.clipboard.writeText()` works from a panel click with **no
`clipboardWrite` permission declared** — verified. Do not add that permission; it costs *"Modify
data you copy and paste"* for nothing.

## VB-41 · The button cluster
Replace the docked nav's current treatment:
- **Text/icon buttons, no containers** — drop the button boxes entirely.
- **Remove the fade above the panel** — VB-22's gradient goes away. Colour alone makes the
  transition smooth enough.
- **A fixed cluster, centred horizontally**, with **padding above the drawer** so there is clear
  visual space between the buttons and the grab handle — today they are close enough to be
  mistaken for each other.

**The accessibility catch**: dropping the containers removes the buttons' backgrounds, so contrast
is now measured against whatever is behind them, and the focus ring has no box to hug. Both need
solving explicitly — `docs/GUARDRAILS.md` requires ≥4.5:1 text contrast, a visible 2px focus ring,
and a ≥44×44 target even when the *painted* control is smaller. VB-15 solved exactly that split for
the deep-dive chips (30px painted, 44px target) — reuse that approach.

Removing VB-22's gradient also removes the machinery that made contrast hold across the drag. Check
whether `src/core/drawer/chrome.ts` and its contrast assertions become dead code or get repointed.
