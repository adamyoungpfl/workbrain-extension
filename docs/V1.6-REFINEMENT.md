## VB-29 · A white frame around the drawer
Extend a white border down the sides and across the bottom of the drawer, so the panel reads as
one app with a framed pane inside it rather than a surface that runs off the edge.

Today the drawer bleeds edge to edge. The frame should read as the app's own margin — consistent
with the panel's existing 14px card radius and the `--canvas` ground the rest of the surface uses.

**Accept**: frame present on left, right and bottom at every drawer height and in both modes; the
drawer's own rounding agrees with the panel's; nothing inside the drawer is clipped by it; the
frame does not eat into the 44px controls at the drawer's edges.

## VB-30 · One solid piece — the mode bar always takes the Brain field
VB-22 made the Brain/List bar adapt to its mode: dark in Brain, light in List. **Change it:** the
bar takes the Brain visual's dark field **in both modes**, with light icons and light text, so the
bar and the visual below read as a single object rather than a strip sitting on one.

That includes the section count on the right, which goes light and stays light.

**This interacts with VB-22's gradient**, which ramps the nav above from the stage colour into the
panel white. If the bar is always dark, the ramp's foot is always dark too — check the nav buttons'
contrast at every drag position in **both** modes, not just Brain. VB-22 already added
`src/core/color/contrast.ts` and asserts computed contrast at several drag positions; extend those
assertions rather than writing new ones.

**Accept**: the bar is the same dark field in Brain and List; icons and count are light in both;
contrast holds for every nav control at min/mid/max drag in both modes; axe-clean.

## VB-31 · The detail zoom, centred and free-floating
On the sub-node detail view, keep the feature node exactly where it is. Change the text:

- **Centred horizontally on the node**, not offset beside it.
- **Free-floating** — no panel, no card, no box around it.
- **Structured identically every time**, so the shape is predictable even though the content is not.

The goal is modern and sleek. Today it is a bordered panel at `left: 35%`; this is a real
restyle, not a tweak.

**Two constraints the current build solved and this must not lose** (see VB-27's notes): the text
must never occlude the node it describes, and it must fit the smallest stage Brain opens at
(260px) without clipping — `scrollHeight <= clientHeight` is already asserted, keep it.

Losing the panel background means the text sits directly on the field, so **contrast becomes the
risk**: assert computed contrast against the actual field colour, not against an assumed value.

**Accept**: text centred on the node, no container, same structure for every node; never occludes
the node; fits 260px; contrast ≥4.5:1 measured against the real field; reduced motion and keyboard
paths unchanged.

## VB-32 · The orbs become the list
The Brain→List morph exists (VB-14b) — nodes fly from their projected globe positions to their list
row positions. Adam wants it **back, and legible as itself**: the orb from the Brain visual visibly
*becomes* the node on the list row.

**First determine whether it regressed or was merely never prominent.** VB-19's section-health work
already had to restore `.filetree-glyph`'s box because `core/drawer/mode.ts`'s `endOf` sizes every
flying node from it, and VB-30's restyle plus VB-33's new rows both move that landing target again.
If the morph still runs correctly, this is about making the arrival read — the orb should land *as*
the row's own status glyph, not fade out near it.

**Accept**: an orb's flight ends on the row's own glyph, at its size and position; the morph runs
in both directions and is interruptible; sampled positions mid-transition prove the nodes are in
flight rather than teleported; reduced motion switches instantly with everything reachable.

## VB-33 · The list as a modern accordion
*Written from description only — the reference image did not arrive.*

Restyle List mode from the terminal-ish tree into a set of **collapsible section rows**, each
opening to its sub-nodes. Per row:

- **X of Y answered**, which VB-19 already computes and renders
- **Y% complete**
- **freshness**, which VB-19 already renders as "answered 2 days ago"
- **a colour indicating incomplete or stale**

**On the percentage and the guardrail.** `docs/GUARDRAILS.md` bans "a composite score out of 100."
A per-section completion percentage is **not** that — it is one real ratio (answered ÷ total), the
same kind of number `docs/design-system.html` already sanctions in "60% of your AI use, set up".
What stays banned is rolling several dimensions into one invented index. Say so in a comment so a
later reader doesn't mistake this for drift.

**Most of the data already exists** — `core/flow/sectionHealth` (VB-19) computes the five states,
the counts, and the staleness per section, and the accordion behaviour is already in `FileTree`
(one section open at a time, auto-syncing to the active one). This is largely a restyle over
existing derivation, not new logic. Confirm before building anything new.

**Colour cannot be the only signal** (`docs/GUARDRAILS.md`). VB-19's glyph column already carries
state without colour and its greyscale test proves it — keep both.

**Accept**: sections collapse and expand; each shows count, percentage, freshness and state; every
state readable with colour removed (extend VB-19's existing greyscale assertion); the accordion
still auto-follows the active section; rows stay legible at 400px; axe-clean; no composite score
anywhere.
