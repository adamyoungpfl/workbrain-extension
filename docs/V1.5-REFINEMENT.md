# V1.5 — the brain lights up, and starts making suggestions

Fifth round of Adam's notes, captured 2026-08-23. **Not started.**

The through-line: the globe stops being a diagram of progress and becomes a picture of a system
coming alive — and Workbrain starts telling you how to improve it.

---

## VB-24 · Solid orbs, muted and vibrant
Today an unanswered node is a hollow ring, which reads as a placeholder for a future orb rather
than a real part of the model. Every node is a real part of the model from question one.

- **Inactive nodes become solid, in a muted tone.** Complete objects, just dim — the same object
  the active one is, turned down.
- **Active nodes get more vibrant and lit** than they are now, so the difference is brightness and
  saturation, not presence versus absence.

Keep the depth cueing that already works (radius, group opacity, the `.brainglobe-shade` sink).
Muted must not collapse into the field colour — an inactive orb has to stay legible as an orb.

**Accept**: no hollow rings anywhere; an inactive orb is unmistakably an object; active and inactive
are distinguishable by more than colour (brightness plus the existing size/label cues), so the
greyscale test still passes; contrast against the deep field holds at every depth.

## VB-25 · Edges that brighten, and one unified glow at the end
**The edges carry the story.** A connecting branch glows brighter as *both* nodes it joins brighten
— so an edge between two answered sections is bright, an edge with one answered end is mid, and an
edge between two untouched sections is dim. As the interview proceeds, illumination spreads along
the structure rather than appearing node by node.

Implement as a function of both endpoints' states, in `core/`, pure and unit-tested — not as a
render-time special case.

**The complete state.** When every node is **active, complete and fresh**, the whole model resolves
to a **single unified glow colour** — it stops being a network of differently-lit parts and becomes
one lit object. That is the "true work brain," and the product's stated goal is to keep it there.

Two design constraints on that state:
1. **It must be reachable and hold.** Freshness decays (VB-19's half-lives), so the unified state
   is not permanent by default — a section going stale should visibly break it. That is the point:
   the glow is what maintenance buys.
2. **`docs/GUARDRAILS.md` rules out "streaks, badges, gamification, or nudges framed as guilt."**
   A unified glow that represents a true state — everything answered and current — is a *state*,
   and passes. It must not become a reward animation, a congratulation, a streak counter, or a
   thing that guilt-trips someone when it dims. Losing the glow should read as information
   ("something is out of date"), never as punishment. The line is real and easy to cross here.

**Accept**: edge brightness is a pure function of both endpoints, unit-tested at every combination;
the unified state triggers only when all nodes are answered, complete and fresh; a single section
going stale visibly breaks it; the transition into and out of it is a state change, not a
celebration; reduced motion reaches the same visual state without animating into it.

## VB-26 · Node labels as icon lettering
Labels should read like the interface's own label style — the compact uppercase treatment already
used for the question eyebrow — rather than the mono-ish text they carry now.

`design/tokens.json` already defines `type.label` (12px / 650 / +0.08em / uppercase, "2–3 words
max"). Use it, scaled for depth. **The 2–3 word ceiling is the real constraint**: several sections
already truncate ("6. How I Communi…", "9. Context Boundari…"). Add short display names for the
globe rather than clipping full section titles — the file keeps its real names, the globe gets
labels that fit. Put them beside the outline data, not in the component.

**Accept**: labels use the label type treatment; no truncation at any depth or rotation; the full
section name is still available (title/aria) even when the short name is shown.

## VB-27 · The node summary, on hover
Top-level nodes lead to secondary nodes. **Where a secondary node has items, hovering it shows a
floating summary**: what the node is, how many items, their categories, and — the part that makes
this more than a tooltip — **a place recommendations attach**.

Content, all derivable locally from `wb:answers`:
- the node's description (from the outline)
- item count and categories (e.g. My World's entities by `entity_type`)
- real metrics only — counts and dates, never a composite score (`docs/GUARDRAILS.md`)
- any recommendations that apply to this node (see VB-28)

**Hover is not enough on its own.** A hover-only affordance is unreachable by keyboard and on
touch. It must also open on focus and on activation, and dismiss on Escape without moving focus.
This is the most likely accessibility failure in this batch.

**Accept**: opens on hover, focus and activation; dismissible by Escape; never traps focus; content
derived fresh, nothing stored; readable at 400px; axe-clean.

## VB-28 · Recommendations — "always scanning"
The product posture Adam is aiming at: *Workbrain is always scanning and making recommendations to
improve your work-brain estate.* This is the largest item here and the one that needs scoping
before it is built.

**The split that makes it possible without breaking the trust story** — already worked out in
`docs/BACKLOG-file-quality-and-intake.md`, and it applies verbatim:

| | Who judges | Why |
|---|---|---|
| **Structural** — sections empty, questions skipped, one entity where most name several, a section stale past its half-life, an initiative with no success criteria | **The panel, locally** | Pure derivation over answers. No content judgment. Instant, offline, free — satisfies the "works on a plane" guardrail. |
| **Qualitative** — is this answer specific enough, does it actually change output | **The person's own AI** | A judgment about content. `strings.ts` already promises *"The panel never reads or scores it."* Same copy/paste hand-off the proof loop uses. |

**Build the structural half now.** It needs no AI, no network, no new permission, and everything it
needs is already in `wb:answers` plus `core/freshness` and `core/flow/outline.ts`. The qualitative
half is the file-quality backlog and stays parked.

**Three constraints, all from guardrails already in force:**
1. **Real metrics only.** Counts, dates, and named gaps. No composite score, no "brain health: 72%".
2. **Never guilt.** A recommendation says what would help and why; it never scolds, never counts
   days of neglect, never frames absence as failure. "Most people name three or four people here"
   is help. "You've only named one" is a scold.
3. **Dismissible, and quiet.** Recommendations are offers. The person must be able to ignore them
   permanently without the product re-raising them, and there is no notification surface —
   `docs/OPEN.md` #1 already settled that drift is surfaced on open, not pushed.

**Where they surface**: in VB-27's node summary for node-specific ones, and a recommendations
section on Home for the estate-wide view. Home already has the next-move card (R1-12); this either
extends it or sits beside it — decide deliberately rather than shipping two competing "what to do
next" surfaces on one screen.

**Open, needs Adam**: how many recommendations show at once (one strong one beats five weak ones);
whether dismissal is permanent or seasonal; and whether a recommendation ever links to the paid
human services the spec says this product qualifies people for, or stays purely self-serve.

**Accept**: recommendations derived purely from stored answers, on every render, nothing persisted
except dismissals; no composite score anywhere; every one names a concrete next action; dismissible
and stays dismissed; works offline; reading level holds; axe-clean.
