# V1.9 — the lower panel becomes an app

Ninth round, captured 2026-08-24 from a PowerPoint mockup. **Not started.**

**Read the collision note first.** V1.8 is building right now and VB-47 puts a file-type toggle
*above* the list. This batch puts a mode toggle in a bar *below* the visual. Those are two toggle
bars on one panel unless they are reconciled deliberately.

---

## What the mockup shows
Top to bottom, all inside the lower panel:
- a **drag handle**, centred at the very top
- **Back** hard left; **Next** and **Skip** hard right — a nav row *inside* the panel's top edge
- a **breadcrumb**: `workbrain > context > how I think`, with **`2/2`** right-aligned
- the **visual** (brain or list), filling the middle
- a **bottom bar** carrying the **brain / list** toggle as two icons

Everything is one solid dark colour, top edge to bottom edge.

## VB-50 · One surface, no tone changes
The whole panel is a single colour. No hover tint, no pressed state, no "default to background" —
buttons through to the bottom bar read as one fluid piece of app rather than controls sitting on a
surface.

**The constraint this creates, and it is not negotiable.** `docs/GUARDRAILS.md` requires a visible
focus state on everything focusable ("2px `--primary` ring, 2px offset — never `outline: none`
without an equal replacement") and forbids distinguishing anything by colour alone. "No tone change
on click" is fine — a pressed state is not required. **A focus state is.** So the answer is a ring,
a weight change, or a mark, not a background tint. Say which, and assert it.

Also note VB-29 (V1.6) put a **white frame** down the drawer's sides and bottom, and VB-30 made the
mode bar take the dark field. A single edge-to-edge colour removes that frame. That is a reversal
of a shipped decision, not an oversight — record it as intended.

## VB-51 · The mode toggle moves to a bottom bar
Brain / list becomes two icons in a bar **below the visual**, not a strip above it.

**⚠️ This collides with VB-47, in flight right now.** V1.8's decision was *"the drawer toggle is the
switcher; Home is a landing page"* — and VB-47 puts a **file-type** toggle (Context / Skills /
Actions) where the "not yet" tag was, above the list. This item adds a **view-mode** toggle
(brain / list) at the bottom.

They are different toggles — *which file* versus *how to look at it* — so both can legitimately
exist. But two toggle bars sandwiching one visual needs deciding on purpose:
- **file** above, **view** below (what the two specs literally say), or
- both in the bottom bar, or
- file moves to the breadcrumb (see VB-52, which already names the file) and only view stays a
  toggle.

**The third is worth serious consideration** — the breadcrumb in the mockup already reads
`workbrain > context > …`, which *is* a file switcher if its segments are pressable. That would
leave exactly one toggle bar and no redundancy. Decide before either is built further.

## VB-52 · Breadcrumbs
`workbrain > context > how I think`, with `2/2` right-aligned — navigation, and an alternative to
the buttons on the list view.

**Reconcile with `FlowProgress`**, which today renders the module title plus a numberless bar above
the question and was deliberately designed that way (VB-02: no printed count, because "a running
count is a number people bargain with"; the count lives in `aria-valuetext` for assistive tech).
The mockup prints `2/2`. That is a reversal — legitimate, but it should be a decision, and it
should not result in the panel carrying both a breadcrumb count and a progress bar saying the same
thing two ways.

Note the breadcrumb's three levels map exactly onto VB-48's tiers (work brain → file → section),
which is the same navigation model arriving from a different direction. **Build them as one thing.**

## VB-53 · Buttons melt into the bar and rise back out
The distinctive ask. On advancing, the nav buttons **melt down into the bar**, and only the buttons
valid for the next question **rise back out** to reform. A living panel rather than a static one.

This is a genuinely good idea and it is the riskiest thing in the batch, for one reason: **it sits
on the path of every single answer.** Forty-nine questions means forty-nine melts. The rules that
have held all product long apply hardest here:
- It must **never gate input.** Next must be pressable the instant the next question is readable,
  not when the animation finishes. VB-10's typewriter holds exactly this line — follow it.
- Keep it **short**. `docs/design-system.html` §06 gives 200ms as the default for anything that
  moves; a melt-and-rise that reads as ceremony at 200ms will read as a delay at 400.
- `prefers-reduced-motion`: buttons simply change. No melt, no rise, same end state.

The behaviour is already derivable — `Flow` knows which controls a position offers (Skip only on
skippable questions, Back only with history). This is presentation over existing truth.

## VB-54 · Lit orbs — a fixed light source
Nodes and edges more vibrant, with depth, and **a fixed point used for shading the orbs**.

This is the right instinct and it is a real upgrade. VB-24 made orbs solid colour deliberately —
the previous gradient had a highlight baked into each orb's own local space, so every orb was lit
from its own top-left regardless of where it sat. **A single scene light fixes exactly that**: one
fixed position, every orb's highlight and terminator computed from *its own* position relative to
that light. That is what makes a group of spheres read as one lit object rather than a set of
stickers.

Put the lighting maths in `src/core/globe/` as a pure function of (orb position, light position) →
(highlight offset, shade) so it is unit-testable and so **both the globe and the list rows use the
same lit orb** (V1.8's VB-45 puts orbs in the rows).

Constraints that must survive: the **unified glow** complete state (VB-25), the **greyscale**
requirement (VB-45 — state cannot be carried by colour or shading alone), and contrast of any text
sitting over the field.

## DECISIONS — settled 2026-08-24

1. **ONE toggle bar. The breadcrumb switches files; the bottom bar switches view.**
   The breadcrumb's segments become pressable — `workbrain > context > how I think` is already a
   file switcher if you can press `context`. VB-47's file toggle above the list is **removed** and
   its behaviour moves into the breadcrumb; the bottom bar carries brain/list only.
   The three segments map exactly onto VB-48's tiers (work brain → file → section), so **the
   breadcrumb and the work-brain zoom are one navigation model** and must share state: pressing a
   segment and zooming out in Brain are the same action by two routes.
   VB-47's storage work (one answers key per flow) is untouched and still correct — only its
   control surface moves.

2. **Keep both the bar and the count.** The slim progress bar stays above the question; the
   breadcrumb carries `2/2` inside the drawer. Different surfaces, different jobs — the bar is felt
   at a glance while answering, the count is read when navigating. VB-02's reasoning (a printed
   count invites bargaining) is respected where it applied: **the question screen still prints no
   number.** The drawer is a navigation surface, and a count there is orientation, not pressure.

3. **Focus is carried by a ring**, not a tone change. `docs/GUARDRAILS.md` already specifies it:
   2px `--primary`, 2px offset, never `outline: none` without an equal replacement. "No tone change
   on click" removes the *tint*, not the ring. Pressed states may go; focus states may not.

4. **The white frame goes.** VB-29 (V1.6) put white down the drawer's sides and bottom; one
   edge-to-edge colour is the whole point of VB-50 and removes it. A deliberate reversal of a
   shipped decision, recorded as intended.
