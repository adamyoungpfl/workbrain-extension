## VB-20 · "Another role?" at the end of the roles loop
After the last seeded role's questions, ask whether there's another to add — so the flow knows
whether to loop back or move on.

**This is a real change to a deliberately-different block, and it has a data-loss trap.**
`roles` is the one **seeded** repeatable (`source.ts:397`): its record count comes from the
`role_names` multi-select, and it carries `addAnotherPrompt: ""` precisely so it never asks.
`runner.ts:114` enforces that — `if (node.seedFrom) continue` skips the add-another branch for
seeded blocks.

The trap: `reconcileSeededRepeatable` rebuilds the record array with
`selectedValues.map(...)`. **Any record whose `role_name` isn't in `role_names` is silently
dropped the next time that question is re-answered.** So an ad-hoc role added at the end of the
loop would vanish the moment someone went Back and touched `role_names` — losing four answered
questions with no warning. That violates "never lose an answer silently"
(`docs/GUARDRAILS.md`'s degradation table).

**The fix, and it is the whole design:** adding a role must **also append it to `role_names`**, so
the seed answer and the records stay in sync and reconcile becomes a no-op rather than a deletion.
The new name has to come from somewhere — most likely a short text prompt ("What's it called?")
matching how `allowCustom` already adds an off-list role.

Decide and record: does the new role slot in as a **custom option** on `role_names` (consistent
with `allowCustom`, and it survives a re-answer because it's a real selected value), or as a record
the reconcile is taught to preserve (more code, more ways to drift)? The first is strongly
preferred.

**Accept**: adding a role appends to both `role_names` and `repeatables.roles`; going Back to
`role_names` and re-submitting **does not** drop it (assert this explicitly — it's the whole
point); answering "no" moves forward; the loop is re-enterable; existing seeded behaviour for the
originally-picked roles is unchanged.

**DECIDED, and built: the custom option.** `applySeededAddAnother` (`core/flow/runner.ts`) writes
the typed name to `role_names` *and* the record it seeds, in one step, so the next reconcile finds
the record by its own name and keeps it — a no-op instead of a deletion. `reconcile` is unchanged;
nothing learned about orphans, because none are created. Three things followed from it:

- **A name can't be a duplicate.** `reconcile` matches a record by name, so two entries sharing one
  would collapse into a single record and lose the second one's answers — the same silent loss by
  another route. `seededNameTaken` refuses it, and the screen says so.
- **`addAnotherPrompt: ""` now carries the whole rule.** `runner.ts`'s `if (node.seedFrom)
  continue` is gone; `""` means "never asks" for every block, which is what the schema always said.
  The prompt and the naming question are attached by `adapter.ts` from `core/flow/addAnother.ts` —
  `source.ts` stays the un-edited port.
- **Off-list values now render as pills** (`core/flow/customOptions.ts`). Without it the added role
  came Back to `role_names` selected but invisible — it survived, but nobody could see that it had.

## VB-21 · Backlog — bulk role import
Not for this sprint. Someone with fifty roles cannot answer four questions fifty times.

Sketch: download a template, populate it offline, upload it back. **Check the existing machinery
first** — `core/files/parse.ts` + `restore.ts` already read a structured file into `Answers`,
including repeatable records, and R1-10's import flow already exists. A roles template is plausibly
a narrow slice of that rather than a second importer. The same "review what came in" question
raised by `docs/PROPOSAL-estate-connector.md` and `docs/BACKLOG-file-quality-and-intake.md` applies
here too — three features now want it; it should be designed once.

Open: file format (CSV is friendlier for fifty rows than Markdown, but adds a parser); whether the
template is generated from live data or is a static download; and whether this belongs in the panel
at all versus the site.

## VB-22 · The drawer's chrome becomes one surface
Today the mode switch and the nav read as strips stacked on the drawer. They should read as the
drawer's own edge.

- **The Brain/List bar takes the stage's colour**, continuing it rather than sitting on it. In
  Brain that means the dark field; toggles become **light icons** (a brain glyph and a list glyph),
  not text on a light chip. The **section count on the right goes light** to match.
- **The nav above it gradates from the stage colour up into the panel white**, and — the specific
  ask — **the fade begins wherever the bar has been dragged to**, so it tracks the handle rather
  than sitting at a fixed height.
- **The buttons must look designed into that gradient, not pasted on top.** Back / Next / Skip sit
  where the colour is changing, so they need treatments that hold at both ends of the ramp.

**The hard constraint this creates**: `docs/GUARDRAILS.md` requires text contrast ≥4.5:1 and
interactive borders ≥3:1 — against a background that is now *moving*. A single button colour cannot
satisfy both ends of a dark-to-white ramp. Options: give the buttons their own solid ground so the
gradient passes behind rather than through them; or interpolate their treatment with the same
variable that drives the gradient. **Whichever is chosen, contrast must be asserted at several drag
positions, not just at rest** — this is the most likely way this batch ships an accessibility
regression.

**Accept**: the bar is visually continuous with the stage in both modes; light iconography in
Brain; the gradient's origin tracks the drag; every nav control clears 4.5:1 at min, mid and max
drag positions (assert computed contrast, don't eyeball); axe-clean throughout; toggles keep real
accessible names, since icons alone are not names.

## VB-23 · The orbs
Refinements to `BrainGlobe`. The zoom timing is confirmed good — don't touch it.

- **Active nodes become solid colour orbs.** Today they carry a gradient with a highlight; make an
  answered node read as a solid, lit sphere.
- **On zoom, remove the halo around the centre orb** — but make the centre **proportionately
  larger** than the sub-nodes ringing it, so hierarchy comes from size rather than glow.
- **Faint connection lines from the centre orb to each outer node**, so the cluster reads as
  attached rather than floating.
- **Clicking a sub-node** moves that orb to a **feature position on the left**, with an
  **information panel on the right** carrying its name and a **grid of its details**.

Note the last one changes the layout inside the stage from centred to a two-column split at 400px
wide. The detail grid will be narrow — check it against the longest real sub-section content
(`2.1 Roles` with several records) before settling the proportions.

**Accept**: answered orbs read as solid at every depth; no halo on the zoomed centre, and its size
alone establishes hierarchy; connection lines present and faint enough not to compete; clicking a
sub-node produces the left-feature / right-detail split; all of it still works under reduced motion
and by keyboard; nothing regresses the existing click-to-navigate.
